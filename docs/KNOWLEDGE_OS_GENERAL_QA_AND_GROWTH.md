# Knowledge OS 通用问答与受控自生长流程

## 目标

系统不以命中固定验收题为目标。每次问题都走同一条运行链：理解问题、检索资料、核验证据、形成回答、绑定引用；回答失败或用户纠错后，形成待审核知识，审核通过才进入后续普通问答。

## 一次问答如何运行

| 阶段 | 系统动作 | 不通过时的处理 |
|---|---|---|
| 1. 接收问题 | 保存原始问题、conversation_id、query_run_id 和可选知识节点范围 | 空问题不执行 |
| 2. 恢复上下文 | 仅继承当前会话中已确认的组织或项目主体 | 有歧义时保留原问题，不把历史答案当事实 |
| 3. 判断问题 | 识别组织、明确项目、年份、专业、指标、列举/计数/比较等意图 | 泛称“多少个项目”不再伪造成项目名称 |
| 4. 生成检索计划 | 形成词法、Dense、文档、章节、表格、关联问法和元数据提示 | 提示用于排序，错误推测不应变成硬过滤 |
| 5. 统一召回 | 汇总冻结来源、已批准补充来源和已审核知识，统一去重排名 | 记录各候选来源与名次 |
| 6. 核验证据 | 检查主体、关系、年份、项目、条件、例外、来源版本和原文支持 | UNKNOWN 进入补证；可靠 MISMATCH 才阻断 |
| 7. 形成答案 | 结构化数据做计算；正文明确陈述的数量直接提取；制度与关系按证据归纳 | 证据不足则拒答，不用模型猜测 |
| 8. 校验回答 | 检查 Claim→Evidence→Citation，保留页码、段落、表格或行号 | 校验失败不显示为“已回答” |
| 9. 返回诊断 | 返回 answer_mode、failure_reason、范围判断和候选来源 | 页面用中文说明下一步 |

## 本次暴露问题的修复

问题“2025年度多少个项目成功打造为设计管理示范项目”曾经失败，但正确正文已经排在候选前两位。根因是两套项目识别规则都把整句误当成项目名称，造成范围 MISMATCH。

现在：

- “多少个/几个/多少项项目”识别为聚合问题，不产生虚假项目范围；
- “星谷科创中心项目”等明确专名仍作为项目；
- 叙述性正文中的明确数量事实可以回答，不强制要求表格；
- 数量、动作、业务主题和年份必须在同一证据句中匹配，避免把“智能建造示范项目”误答成“设计管理示范项目”；
- 找到资料但未通过核验时，页面显示阻断原因和最多3个待核对候选来源。

## 用户反馈如何形成知识

1. 用户点击“纠正这条回答”。
2. 系统自动带入已有引用；没有正式引用时，展示被召回但未通过核验的候选来源。
3. 用户核对正确答案、来源、位置、必要事实、适用范围、相似问和反例。
4. 服务端用 idempotency_key 防止重复提交；用户修改后的反馈形成新记录。
5. 反馈状态从“已记录”进入“待核对来源”和“待业务确认”。
6. 业务负责人确认后，系统只读解析来源并绑定 source_id、source_version 和 evidence_refs。
7. 审核知识以 knowledge_id 和版本保存；标准问、相似问、反例只作为入口，不复制原文。
8. 发布后从普通全库入口重新回归。知识生效和回归通过分别记录。
9. 来源哈希变化时，人工知识转为 REVIEW_REQUIRED，并形成 PROPOSED 变更候选，不静默覆盖。
10. 撤回后标准答案、相似问索引、搜索和问答同步退出；回滚依赖失效来源时仍需复核。

## “自生长”的边界

这里的自生长是“自动发现缺口、生成候选、复用已审核知识并跟踪版本”，不是系统自行把回答写成事实。企业制度、组织关系、数字和项目结论仍由业务负责人最终确认。

系统能持续改善的前提是：

- 来源文件已进入授权范围且正文可解析；
- 反馈填写了可以定位的来源和事实；
- 审核人确认适用范围、版本和必设/选设等边界；
- 新问题持续进入回归集，并保留失败样本。

## 仍然可能失败的环节

- 知识库根本没有相应资料；
- 扫描件、复杂表格或损坏文件没有形成可用正文；
- 文件有正文，但元数据或版本关系错误；
- 不同资料给出冲突数字，无法自动裁决；
- 问题主体、年份或指标含糊；
- 新题型尚未建立可靠的事实提取方法；
- 来源已更新，旧人工知识正在等待复核。

因此，验收结果只能证明已测流程和题型，不能宣称“任意问题都能正确回答”。新的真实失败题应按同一链路定位属于解析、索引、召回、范围、证据、回答还是反馈生效问题，再修共享根因。
